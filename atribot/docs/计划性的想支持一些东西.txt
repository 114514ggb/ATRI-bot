Context condensed
目前的群聊天情况对于大多数情况(就是日常聊天任务，面对对话中有价值的信息量严重不足情况)，我一直采用的是直接截断丢弃的方案
开始考虑加入到指定条件后进行上下文压缩的功能了,可在有长关联性对话保持记忆
做一个优先级系统，会给上下文的工具和对话评定一个优先级然后在上下文不足的时候根据这个进行回收

Context Memory tool 
对于前面的被丢弃的上下文应该，也进行存储，虽然请求时不会携带
因为上面的Context condensed仅仅时进行了总结，可能会顺损失重要的细节部分
对于目前的这个情况就需要模型能主动查询丢弃的上下文了
当然或许也可以支持模型可以编辑管理自己的上下文,自己控制哪些要删除哪些要留,哪些要总结来解决这些问题(?)

Programmatic tool calling
对于json交互还是有些许问题
最好能采用编程的方式进行发言，和搜索什么的和对一些数据进行处理,而不是直接给ai看,比如你问LLM这个一段要处理的文本里面什么词出现了几次,或是其他
模型可以直接编写带有条件或循环的代码来处理数据或发送消息(比如你让LLM从1数到100可以通过循环来调用发消息的方法来一次性实现,但是也需要相应的限制)
模型应不应直接和user交互,而是通过编写代码，再由执行代码解释器执行，给出结果
当然会支持给模型一个单独的工作区,可以处理，并且发送文件
需要一个环境还有一个对自定义命令的解释器

Tool search tool 
对LLM不直接暴露所有工具,但是会有一个用于查找其余工具的tool,查找后会在下一次请求中携带满足条件的工具
对于查询条件可以使用正则表达式或是对自然语言向量化筛选出语义相近的工具
但是为了保证模型不会做什么都去搜索(因为模型不知道他有什么工具不知道能干什么)，需要在上下文中嵌入拥有工具的概况或是工具包式的，需要做那些方面的事情展现什么
对于搜索到的工具存在的时间应该是一轮(从一次user输入,到模型给出完全满足需要的答案了就是一轮)
对于工具的筛选也有很多方案,比如可以根据用户输入，动态给出可能使用工具,不需要LLM主动查询

子代理
LLM可以调用一个工具,把一个被拆分的问题给另一个LLM，并且等待完成，后汇总给出结果
因为ai做一些事情的时候群里历史的上下文都几乎没什么用,在这种情况下LLM执行一个任务的时候(比如查找资料)的过程中会产生不必要的消耗(携带群里没用的上下文影响模型的性能)
子代理,可以根据简单的目标在自己干净的环境里完成目标,给出总结,再让聊天的LLM转述
